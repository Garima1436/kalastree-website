# KalaStree Chat Intelligence Engine — Technical Differentiation

**Purpose:** Separates what this system reuses from well-established technique, what is specific engineering work for KalaStree's situation, and what might be worth a closer prior-art look later. **This document does not claim that any listed item is novel or patentable** — that determination requires a formal prior-art search, which has not been done. Where something looks close to established practice, it's labeled as such rather than hedged.

## 1. Existing / Common Technology

Techniques and patterns used here that are standard practice, well documented elsewhere, or directly analogous to widely-deployed systems:

- **Retrieval-Augmented Generation (RAG) over a vector store.** Chroma + `BAAI/bge-small-en-v1.5` embeddings + an LLM answering from retrieved context is the textbook RAG pattern, already present in the pre-existing Python backend (`rag.py`) before this work started.
- **Intent classification + slot/entity extraction via an LLM in structured-output mode.** A common pattern for building task-oriented assistants (the same shape as, e.g., typical function-calling or JSON-mode extraction pipelines).
- **Hard vs. soft constraint separation for filtering + ranking.** Standard in recommender systems and search/faceted-filtering engines generally (filter first, then score what remains).
- **Weighted linear scoring for ranking** with named, documented factors. A conventional, explainable alternative to a learned ranking model — common wherever transparency matters more than marginal accuracy gains.
- **Retrieval-then-generate grounding with an explicit refusal instruction** ("say you don't know" prompting) is a widely used hallucination-mitigation technique.
- **Metadata/structured-filter retrieval combined with vector search** ("hybrid search") is an established pattern in modern RAG systems, not unique to this implementation.
- **Role-gated debug/admin panels**, **rate limiting**, and **service-role database clients bypassing RLS for trusted server code** are standard web-application engineering, already used elsewhere in the KalaStree codebase before this work.

## 2. KalaStree-Specific Implementation

Engineering decisions and mechanisms shaped specifically by KalaStree's actual data, codebase, and constraints — genuine work product, but mostly applications of the general techniques above to a particular, messy, real system rather than new techniques in themselves:

- **The specific hard/soft constraint set** for this domain: GI-required, state, craft, price ceiling/floor vs. approximate target (distinguished via a `price_mode` field derived from the user's own wording — "under" vs. "around"), and a structurally-always-true "female artisan" constraint reflecting that every artisan on the platform is a woman by the business's own construction, kept for explainability rather than as a real filter.
- **The specific ranking weights and factors** (`constraint_match` 0.30, `semantic_relevance` 0.25, `gi_relevance` 0.20, `cultural_relevance` 0.10, `price_suitability` 0.10, `availability` 0.05) — tuned by judgment to this domain's priorities (constraint satisfaction and GI authenticity over generic relevance), not derived from a learned model or a large evaluation set.
- **The name-token GI-matching heuristic** (`matchesGIRegistry`'s fallback path) — a workaround for a specific, discovered data-quality gap (`products.gi_tag` unpopulated on every live row), matching a product to its GI by checking whether the GI's first significant word appears in the product's name/category/artisan-craft, scoped to state. This is a pragmatic patch for messy real data, not a general contribution.
- **The entity-grounding validator** (`groundInCurrentMessage`) that deterministically strips LLM-extracted "detail" entities (artisan name, material, etc.) unless they're traceable to the literal text of the user's current message — built in direct response to an observed failure mode (the model attributing its own prior answer's content back to the user). This is a narrow, targeted guardrail for a specific bug class discovered during testing here, not a general-purpose technique being introduced for the first time — retrieval-attribution/citation-grounding checks of this general shape exist elsewhere in the RAG literature, though typically applied to answer text rather than to intermediate structured-extraction output.
- **Selective/conditional hybrid retrieval by intent** — calling the vector-store narrative-evidence endpoint only for intents in a defined `NARRATIVE_INTENTS` set, skipping it for pure product lookups — is an efficiency-motivated integration choice specific to how this system's intents are enumerated, not a new retrieval algorithm.
- **The context-completeness distinction** ("product search did not run for this query" vs. "product search ran and found nothing") added to the LLM's context after observing the model conflate the two and assert an artisan had zero products when the search simply hadn't been run for that intent. A specific, discovered bug fix, not a generalizable pattern being newly proposed.
- **The multi-turn memory mechanism carrying a client-held `StructuredQuery` object across turns**, merged with each turn's freshly extracted (and grounding-validated) entities, instead of server-side session state — a stateless design choice matching this API's existing pattern (history was already client-held before this work).

## 3. Features That May Warrant Prior-Art Investigation

Listed because their *combination*, in this specific configuration, is less obviously "textbook" than the items in §1 — not because any individual piece is claimed to be new. A proper search would need to check each against existing commerce-chatbot, RAG-grounding, and structured-extraction-validation literature/patents before drawing any conclusion:

- **The overall pipeline shape**: mandatory deterministic constraint-satisfaction and eligibility filtering interposed between LLM-based query understanding and LLM-based answer generation, where the *first* LLM call is explicitly barred from making any decision the pipeline treats as consequential (GI status, eligibility, price, availability), and the *second* LLM call is only ever allowed to explain decisions already made outside it. The general "constrain the LLM, don't trust it for hard decisions" philosophy is common; this specific staging (extract → normalize → constrain → resolve relationships → verify → retrieve → filter → rank → assemble evidence → generate, each stage typed and independently testable) is more specific than most published "agentic RAG" descriptions we're aware of, but no search has been done to confirm novelty.
- **Deterministic post-hoc validation of LLM-extracted structured entities against the literal source message**, as a distinct pipeline stage separate from both the extraction prompt and the final answer's groundedness check (i.e., grounding-checking the *intermediate* structured representation, not just the final natural-language answer). Most groundedness/hallucination-mitigation techniques we're aware of check the *final answer* against retrieved context; checking an intermediate structured-extraction step against the immediate conversational turn (as opposed to the full retrieved context) is a narrower, more specific check that may or may not already exist under a different name elsewhere.
- **Per-product, per-query GI-registry resolution distinguished from single-entity GI verification** — i.e., treating "is craft X GI-certified" (one entity, one answer) and "which of these N candidate products are GI-certified" (N independent lookups against a shared registry, because a region can have multiple registered GIs) as genuinely different mechanisms with different code paths, rather than one verification function reused loosely for both. Whether this distinction is treated as a separate mechanism elsewhere is unknown without a search.
- **The evidence-driven, source-typed context assembly** feeding a single unified list (mixing database-verified facts and vector-retrieved narrative text, each explicitly tagged with `verification_status`) into one LLM call, where the *system prompt* is the only thing telling the model which facts are authoritative — this is a design choice with a plausible prior-art footprint in commerce/support chatbots specifically (as opposed to general RAG systems), which we have not searched.
